# GM65 床位条码接入

GM65 与现有广角、长焦摄像头并用，不改动 STM32 对准、扫码确认、机械臂或放药状态机，不参与护士台订单二维码。

## 端口与配置

配置在 `2_ROS2包_obstacle_detector/config/scanner.yaml` 的 `code_scanner.ros__parameters`：

- `gm65_enabled: true`
- `gm65_device: /dev/serial/by-id/usb-USBKey_Chip_USBKey_Module_202730041341-if00`
- `gm65_baud: 9600`

使用稳定设备名称，不依赖 `/dev/ttyACM1` 编号，不搜索或打开 STM32、摄像头的其他串口。沿用已有 python3-serial 依赖和 code_scanner 启动入口，无须修改部署、启动服务或烧录 STM32。

## 接收条件

1. 当前任务为前往 Bed1 / Bed3 或该床扫码阶段（状态 3 / 4 / 6 / 7）。
2. 车辆处于当前目标床位停车点 1.5 m 内，沿用摄像头的空间门控；这允许在到床前提前缓存条码，并非仅停车后接收。
3. 任务状态和位置更新均不超过 0.5 s。
4. 收到的完整条码必须匹配现有六个床位条码白名单。订单 `11/13/31/33` 不接受。

GM65 一帧即可确认，摄像头仍要求两次命中。同床本轮第一个有效结果生效，后续来源不覆盖。结果仍发布到 `/medical_nav/scan_result`，GM65 的 `source` 为 `gm65`，继续使用既有桥接和 STM32 确认协议。提前扫码不等于立即放药：对准、机械臂以及扫码超时处理均保持原有逻辑。

对准状态 12 / 13 不新增接收窗口，与原摄像头逻辑一致。之前已缓存的条码仍有效，离开对准进入床位扫码状态后可继续接收新结果。

## 串口与故障处理

仅接收完整 ASCII 白名单值，CR / LF 结束一帧；无结束符时等待 100 ms 无新字节再确认。未验证的前缀、后缀、乱码、超长帧均拒绝，不从错误报文中截取有效子串。

串口以非阻塞方式读取，每次最多处理 512 字节；过量积压直接丢弃。打开端口、切换任务、进入或离开接收区域、任务重置、重连、超过 0.5 s 未轮询时都清除旧数据，防止将先前扫到的条码带入新床位。

USB 拔出、权限不足、端口被占用时，记录错误并每 2 s 重试，不等待设备就绪、不停止摄像头。设备由当前用户读取，需具备串口权限；调试用 `cat` 等读取进程应先退出。

这里只限制软件接收结果，不向 GM65 下发开关光源、蜂鸣或改变扫码模式的命令。模块自身仍可能亮灯、鸣叫，但非床位窗口的数据会被丢弃。

## 验证

部署后，在正常 ROS 环境中读取状态：

```bash
ros2 topic echo /medical_nav/scanner_status std_msgs/msg/String --once --full-length
```

新增字段为 `gm65_enabled`、`gm65_connected`、`gm65_active`、`gm65_device`、`gm65_error`。`connected=true` 仅代表串口已打开，不证明模块已经输出条码。

```bash
ros2 topic echo /medical_nav/scan_result std_msgs/msg/String \
  --field data --full-length --filter "'gm65' in m.data"
```

应在安全测试条件下验证：护士台不产生 GM65 结果；当前目标床位区域内单帧产生结果；摄像头先确认后 GM65 不覆盖；USB 重插后恢复且不重放旧条码。没有 STM32 任务和新鲜位置时，正常流程拒绝 GM65 结果。
