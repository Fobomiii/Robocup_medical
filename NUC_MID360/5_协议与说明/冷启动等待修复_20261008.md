# 冷启动一直显示“等待”的检查与修复

记录时间：2026-10-08 21:48（北京时间）。

本轮针对“冷启动后一直等待、按钮无反应”检查 STM32 任务状态、串口桥接、Nav2 action、路径放行和界面链路。修改已落在本地工作区，尚未部署到 NUC，也没有本轮实车冷启动日志；下面区分已复现的软件缺陷与待实机验证的环节。

## 已确认的缺陷

| 原代码行为 | 为什么可能一直等待 | 本轮处理 |
| --- | --- | --- |
| STM32 还在等待按钮时就发送 NavigateToPose | 底盘禁止运动，但 FollowPath 的进度检查、护士台点位超时已经运行，可能提前失败或切换点位 | 按钮前只用 ComputePathToPose 预规划，按钮后才启动实际导航 |
| action 在启动期间被拒绝，最多重试 20 次 | 第 21 次进入 NAV_ERROR；同一请求再来被视为已结束，只重复错误，不再尝试 | 预规划的拒绝、空路径、超时、通信异常都保留请求并重试，不进入任务终态 |
| /plan 必须在 action 接受回调之后到达才计为有效 | ROS 两个通道独立，首条路径可能先到，因而错失 plan_ready | 保留本次发送后、地图坐标系及目标终点匹配的候选路径，在接受回调补齐就绪状态 |
| 等待态中 FOLLOWING→WAIT_PATH 被当作 STM32 重启 | 普通预规划刷新失败也会产生该变化，误清目标和请求编号 | 连续位姿遥测下不再仅凭导航状态下降判定重启；真正返回初始任务或遥测中断的清理仍保留 |
| STM32 收到 FOLLOWING 后停止重发目标 | 导航器进程重启或订阅较晚时，可能收不到桥接已经保存的目标 | 等待发车期间，若导航器状态过期或请求不匹配，桥接每秒重发当前目标；任务重置后不重发已清除的目标 |
| 等待发车期间收到摄像头原始扫码结果就清除待执行导航目标 | 扫码尚未得到 STM32 接受确认，原目标却已丢失 | 等待期间保留目标，按 STM32 确认后的任务状态与新目标请求切换 |

对 HEAD（c95758d）的旧导航器进行 ROS 边界替身复现，实际运行旧生产代码，得到：

```text
before button, NavigateToPose sent: 1
after 21 rejects: 4 False rejected
after MCU repeats same request: 4 False rejected
```

其中 4 为 NAV_ERROR，False 为 busy。这说明单纯增大启动延时或只放宽 STM32 等待状态，无法消除这条永久错误链路。此复现证明软件缺陷存在，并不能证明本次实车只遇到了这一种故障。

## 修改后的交接

1. 桥接收到 STM32 的位姿、轮速、任务状态和目标请求。三个等待态 14/15/16 都允许静止遥测恢复确认；连续健康静止确认保持原有 0.75 秒要求。
2. 导航器排队当前目标，异步查询 map_server、planner_server、controller_server、bt_navigator、velocity_smoother、collision_monitor 的生命周期状态。action 能被发现不等于节点已经激活。
3. 节点 active 且状态新鲜后，只预规划当前任务匹配的目标。ComputePathToPose 成功且返回非空、地图坐标系正确、终点匹配的路径后，报告 plan_ready 与 NAV_FOLLOWING。
4. 桥接将相同 request_id/goal_id 的 NAV_FOLLOWING 发给 STM32；STM32 位姿回报也确认该状态后，界面显示“发车”。此时仍处于等待任务态，NUC 与 STM32 两侧都不允许底盘运动。
5. 按钮使 STM32 从等待态进入相应导航态。导航器不再依赖第二条目标请求，直接启动已排队目标的 NavigateToPose。预规划结果立即失去运动放行资格，必须再取得本次执行的有效路径。
6. 护士台点位的 6 秒超时从按下按钮且实际 action 被接受后开始；久等按钮不会轮换点位。

预规划默认每秒刷新；单次超过 5 秒按超时重试，旧请求的迟到回调不能放行新目标。查询到的生命周期状态超过 3 秒未刷新，会撤销发车就绪。导航器进程启用了 2 秒后重启，并配合桥接目标重发恢复等待中的任务。

“等待”下面新增具体原因，可区分串口未连、位姿/轮速遥测未齐、等待底盘静止、哪个 Nav2 节点未激活、预规划正在重试、等待 STM32 确认。生命周期未激活仍会阻止发车。2026-10-09 补充：`start_obstacle.sh` 现在会对七个关键生命周期节点执行有界启动验收；75 秒内未全部连续 active 时主动退出，由 systemd 自动重启整套导航。`start_mid360.sh` 也会验证 `/livox/lidar` 确实产生点云，而不是只确认驱动进程存在；30 秒无首帧就退出并由 `mid360.service` 不限次数重试。导航启动前再次等待点云，超时同样失败重试。因此“雷达进程假在线”和“Nav2 节点停在 inactive”都不再需要人工第二次重启。该机制只恢复失败的冷启动，不跳过任何安全或任务放行条件。

## 验证情况

- 冷启动导航器与真实桥接回调测试：32 项通过。使用 ROS transport/action/service 替身，运行生产构造器、计时器和回调；串口输出用真实协议编码器及解析器验证。
- 桥接安全测试：53 项通过。
- 界面状态与等待原因测试：11 项通过。
- 覆盖请求/遥测/任务消息乱序、30 次预规划拒绝后恢复、未激活节点、按按钮后没有第二条请求、超时与迟到回调、首条路径先于 action 接受、旧目标路径、遥测断开、预发车扫码、导航器重启重发、STM32 状态交接以及等待态不可运动。
- 修改的 Python 文件通过语法编译，package.xml 可解析。扫码界面禁用 Qt 自动 DPI 放大，相机控件不再按宽度强制反推高度；广角和长焦的打开/释放通过同一互斥锁原子交接，避免部署重启或任务切换时两个线程同时占用 V4L2 设备。长焦仍有 45 秒“设备未打开”故障超时，但正常出帧后不再使用会被部署过程提前耗尽的 15 秒扫码窗口，而是保持到预发车任务变化。没有本轮 Qt 实际显示、DDS/真实 Nav2 action、串口硬件或车辆冷启动验收。
- 全套 Windows 检查另有两个 ROS 依赖导入错误（sensor_msgs、rclpy），以及一项既有 MPPI 参数与旧断言不一致：heading vx_std 当前为 1.0，测试要求 0.8。本轮保留现有 MPPI 调参。
- 本轮改动文件的 diff 检查无新增空白错误；全工作区 diff 检查仍报告本轮之前 NUC操作.txt 的两处尾部空白。

## 部署与实机验收

本轮修改集中在 NUC 的 ROS 包，未改 STM32 协议和固件，不需要因本轮改动重新烧录。仅更新电脑上的源文件不会影响车辆，必须将修改后的 obstacle_detector 包同步到 NUC 工作区，再重新构建并重启导航服务与扫码界面。

NUC 工作区为 /home/fzurobot/livox_ws。包同步完成后，在 NUC 上构建：

```bash
set +u
source /opt/ros/humble/setup.bash
cd /home/fzurobot/livox_ws
colcon build --symlink-install --packages-select obstacle_detector
```

构建成功后重启 obstacle-detector.service，并重新打开扫码界面，使两者加载新安装代码。服务的 dry_run=false 会允许真实运动，测试时必须保留等待按钮流程，并使用已准备好的测试场地。

本仓库 deploy_nuc.py 会同步、构建并重启服务，也会部署其他当前工作区修改。其默认 MEDICAL_NAV_DRY_RUN=false；若使用它做首次静止检查，先显式设置 MEDICAL_NAV_DRY_RUN=true。静止检查不能代替实际按按钮后运动的验收。

实机验收建议至少连续进行五次整车断电冷启动，包含扫码前后两种启动情况：

- 未按按钮，界面由“等待”进入“发车”，底盘保持静止。等待超过 30 秒，护士台点位仍不应因 6 秒计时轮换。
- 原点完成订单扫码后，任务 14 应变为 15 或 16；对应床位路径就绪后再次显示“发车”。
- 显示“发车”后重新按按钮，界面变为“运行”，实际导航启动。按钮在路径未就绪时按下仍不会启动，需在就绪后重新按。
- 若仍等待，优先读取界面的具体原因；真实位姿缺失可能来自 STM32 的 OPS/HWT 条件，路径规划失败可能来自地图、TF 或目标有效性，不能当成已确认的导航器重试死锁。

查询时使用与服务相同的 ROS 隔离环境，当前默认 ROS_DOMAIN_ID=77、ROS_LOCALHOST_ONLY=1：

```bash
set +u
set -a
source /home/fzurobot/.config/medical-navigation.env
set +a
source /opt/ros/humble/setup.bash
source /home/fzurobot/livox_ws/install/setup.bash
export ROS_DOMAIN_ID=${ROS_DOMAIN_ID:-77}
export ROS_LOCALHOST_ONLY=${ROS_LOCALHOST_ONLY:-1}
timeout 8s ros2 topic echo --once /medical_nav/bridge_status
timeout 8s ros2 topic echo --once /medical_nav/navigator_status
```

关注 bridge_status.start_gate.reason、stm32.task_state/nav_status、goal_gate 的请求匹配与新鲜度，以及 navigator_status.result/inactive_startup_nodes。只看到 systemd 服务 active 不能证明 Nav2 节点已经 active 或当前目标可发车。
