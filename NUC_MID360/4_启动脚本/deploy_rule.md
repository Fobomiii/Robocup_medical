# Deploy 修改规则

修改 `deploy_nuc.py`、`start_obstacle.sh`、`obstacle-detector.service` 或其他部署/启动链路前，必须完整阅读并遵守本文件。

## 不可破坏的边界

1. 导航部署不得安装、修改或重启 `mid360.service`；只允许检查其状态。
2. 不得恢复 `medical_nav_current` 或任何 release 软链接切换方案。部署目标始终是固定工作区。
3. 部署期间不得执行全路线规划、路线预检或其他会争抢 Nav2 生命周期服务的 ROS 请求。
4. 机器人可能已授权运动或仍在运动时，必须拒绝重启导航服务。
5. 必须先完成文件同步和构建，构建成功后才允许重启服务。
6. 只能由一个权威启动探针判定导航是否真正就绪；`systemd active` 不能单独视为成功。
7. `obstacle-detector.service` 必须使用 `Type=notify`，仅在启动探针通过后通知 systemd 已就绪。
8. STM32 短暂遥测抖动不得重置比赛任务；只有确认任务 epoch 变化后才能重置任务状态。

## 超时与重试

1. SSH、远程命令、构建、systemd 操作和就绪等待都必须有明确的总超时。
2. 启动最多允许三次受控尝试；不得使用无限 `Restart=` 循环。
3. 自动重试必须由一次 deploy 完整等待完成，不得依赖用户反复手动执行 deploy。
4. 失败后保留无分页的 `systemctl` 和 `journalctl` 诊断，禁止进入 pager 阻塞终端。
5. 运行依赖只在确认缺失时安装，不能每次部署都执行无条件安装。

## 结果与退出码

1. 成功的最后一行必须是绿色 `[deploy] SUCCEEDED`，进程退出码必须为 `0`。
2. 任何失败、异常或用户中断的最后一行必须是红色 `[deploy] FAILED`，进程退出码必须非 `0`。
3. 异常堆栈和失败诊断必须先输出，结果横幅必须是整个 deploy 的最后输出。
4. 禁止吞掉失败后继续打印“部署完成”，也禁止仅凭某个中间步骤成功就输出成功横幅。

## 修改后验证

每次修改部署链路至少完成以下检查：

1. `python -m py_compile NUC_MID360/4_启动脚本/deploy_nuc.py`
2. `bash -n NUC_MID360/4_启动脚本/start_obstacle.sh`
3. 运行部署和启动链路相关的定向测试。
4. 在条件允许时运行完整测试集。
5. `git diff --check`
6. 验证正常返回、参数错误、未捕获异常和 `Ctrl+C` 的最后一行及退出码。

任何新功能若与上述规则冲突，必须先停止修改并重新设计，不能用延长等待、增加无限重试或要求重复运行 deploy 来掩盖问题。
