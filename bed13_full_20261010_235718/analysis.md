# `bed13_full_20261010_235718` 分析

分析时间：2026-10-11。数据包包含三次完整的 `home -> bed1 -> bed3 -> home` 运行、RVIZ 视频和 costmap/规划/控制话题。它**没有**录到原始点云、过滤点云、`ops_raw_pose`、`ops_calibration` 和地图，因此不能逐点追溯每一个假障碍的原始雷达回波。以下把“已经由录包和代码共同证实”的结论与“合理但尚不能定量证实”的判断分开。

## 结论

1. 床3后方的大片鬼影不是机械臂反射。该问题在未安装机械臂时已经存在；而且本次第二次运行在床3对准前、校准改变量仅约 3 mm 时，global costmap 中已经有显著额外 lethal 格子。因此不能把现象归因于机械臂。
2. 已确认存在一个时间坐标系不一致：锥桶补充轨迹先按**原始点云时间**存入 `odom`，再按**最新 TF**变回雷达帧；但输出点云仍携带原始时间戳。车在运动时，同一个补充圆盘会被 costmap 按旧时刻再次变换，位置就会错开。它能够产生并维持移动时的离散假障碍/膨胀团，是目前最直接、可修复的根因。
3. 床3过冲不是单纯 STM32 轮速斜坡造成。MPPI 已经要求反向，但 NUC 的 closed-loop speed smoother 仍持续输出原方向，之后 STM32 目标和实测轮速才依次反向。优化失败、Approach 行为和路径重规划还会使第三次运行的反向过程反复。
4. 床3开始的折线路径并非“明明能直走却无故绕路”。采样到的 global costmap 中，从当时起点直连床3的线段包含 `253/254` 高代价/阻塞格；过冲到另一侧后，直线不再穿过这些格子，于是规划路径才变得接近直线。鬼影会让这件事更频繁，但实际障碍、膨胀和全局规划器的时间模型也参与其中。
5. 因此不要先通过减小 `inflation_radius`、强制直线或继续提高速度来掩盖现象。第一优先级是使障碍点的坐标和时间戳一致，并在 OPS 校准跳变时处理历史障碍缓存；否则加速只会扩大过冲和错误重规划的代价。

## 1. 鬼影：机械臂不是根因

### 录包现象

以运行开始时护士台附近 ROI（`x=1..3 m, y=-0.6..1.6 m`）的 lethal 格子为参考：

| 床3校准前后 | 校准 offset 改变量 | 校准前额外 lethal | 校准后仍保留 | 校准后新出现 |
|---|---:|---:|---:|---:|
| 第1次 | 111.8 mm | 5 | 5 | 43 |
| 第2次 | 3.0 mm | 76 | 60 | 17 |
| 第3次 | 74.6 mm | 30 | 16 | 30 |

这里的“额外”是相对第一帧，并不代表每个格子都一定是假障碍；但第2次校准几乎没有位移、校准前仍已有 76 个额外 lethal 格，足以排除“床位校准跳变是唯一原因”。同样，既然机械臂安装前已有该现象，机械臂也不是根因。

锥桶补充状态持续出现大量历史轨迹：例如运行中有 `raw_clusters=6-9`、`merged_cones=5-9`，但 `held_tracks=14-25`。每一个补充中心会合成半径 `0.18 m` 的圆盘；一旦中心错位，`0.60 m / 8.0` 的 inflation 会放大它的可见范围。inflation 放大现有 lethal 源，但不制造 lethal 源。

### 已确认的代码缺陷

`cone_footprint.py` 中：

1. `_to_persistence_frame(..., stamp)` 使用点云的原始时间戳，将检测中心保存到 `odom`（约第 274 行）。这是正确的第一步。
2. `_from_persistence_frame(...)` 调用 `_lookup(...)` 时不再传 `stamp`（约第 290 行），因此使用最新 `odom -> lidar` TF。
3. 合成后的 held 圆盘与当前点云合并（约第 401 行），但发布 header 仍是 `message.header.stamp`（约第 418-421 行）。

这三步组合起来的结果是：圆盘坐标对应“现在的车位”，header 却声明“过去的点云时刻”。costmap 随后会依据 header 的旧时刻把它再变换一次。机器人高速横移/转向时，该误差足以使静态障碍变成拖尾或偏移的圆形膨胀团。

### 其他放大因素，但不能取代上述根因

- `persistence_s=0.60 s`、匹配距离 `0.40 m`、中心合并距离 `0.28 m`，对非重复扫描而言较容易把相邻碎片留成历史补充点。
- 分类器只使用 XY 连通性、点数、XY/Z 跨度和最低点高度；没有验证圆锥形状。墙角、床腿或家具碎片可能被误判为锥桶。原始点云未录制，无法把本包中的某一个中心逐点定性为误判。
- global/local 同时以 `/livox/lidar_nav` 做 marking 和 clearing。补充圆盘并不是实际激光射线端点，而地面/高度过滤会减少清除射线，因此旧 marking 不一定能迅速被清掉。
- OPS 床位校准当前直接改变 `odom -> base_link`；历史障碍却保存在 `odom`。运行 1/3 的 `111.8/74.6 mm` 校准会进一步让缓存障碍与视觉地图错开，但第2次证据表明它不是唯一来源。
- 地面平面每帧重新拟合，录包中有 `97` 次拟合失败/fallback；filtered cloud age 通常 `0.105-0.111 s`，最大 `0.152 s`。这会使边界有抖动，但没有原始点云，不能把它量化为该大片鬼影的主因。

### 修复顺序

1. 修复补充轨迹的时间一致性：反变换必须使用 `message.header.stamp`，或将输出 header 改为与“最新 TF”同一时刻。对于给 costmap 的点云，推荐前者：所有点都表达在同一个原始云时刻。修复后补充圆盘不应再随车形成时间错位。
2. OPS 校准时清空 held cone track 和 costmap observation buffer，短期可避免旧 `odom` 坐标残留。长期更合理的 TF 结构是保持 `odom -> base_link` 连续，把绝对校正放在 `map -> odom`，避免里程计跳变。
3. 临时做 A/B：将 `persistence_s` 设为 `0`，仅测试鬼影是否立即明显减少。它会降低锥桶补偿的连续性，不能当最终方案。
4. 录制下一包时加入 `/livox/lidar`、`/livox/lidar_filtered`、`/livox/lidar_nav`、`/livox/lidar_safety`、`/medical_nav/ops_raw_pose`、`/medical_nav/ops_calibration` 和 `/map`。这样才能把假格子追溯到具体的原始簇、滤波输出和 TF。

## 2. 过冲：命令链的定量证据

当前运行的命令链可从录包恢复为：

`MPPI -> velocity smoother -> bed/home filter -> safe filter -> bridge -> STM32 target -> 实测轮速/odom`

第2次 Bed3 在 `23:59:08.623` 发生明显反向：

| 层 | 从 MPPI 首次反向到该层过零 |
|---|---:|
| MPPI | 0.000 s |
| smoother | 1.074 s |
| safe filter / bridge | 1.098 s |
| 推定 STM32 target | 1.169 s |
| 实测 wheel/odom | 1.251 s |

当 MPPI 已要求新方向 `+1.97 m/s` 时，smoother 仍在旧方向约 `-1.02 m/s`，实测轮速约 `-1.15 m/s`。在到达反向前，车继续沿旧地图方向移动 `0.764 m`；以实测车体速度积分为 `0.749 m`，与路径偏差由 `0.307 m` 增至 `0.793 m` 相互印证。

第3次的首次 MPPI 反向在 `23:59:53.834`，但约 `0.25 s` 后 MPPI 又因优化失败改变决策；因此不能把完整 `1.285 m` 的后续轨迹都归咎于一次反向。仅初次连续反向窗口造成的旧方向移动仍约 `0.354 m`（速度积分 `0.346 m`），之后叠加 `Optimizer fail`、Approach 和再规划。

因此：

- STM32 不是主要的额外等待环节。bridge 到 STM32 target 约增加 `0.07 s`，target 到实测轮速再约 `0.10 s`；主要的 `~1.07 s` 已经发生在 NUC speed smoother 的减速过程。
- 当前 `CLOSED_LOOP` 会以实测/平均 odom 速度作为下一次限幅起点。即使 YAML 写了 `max_decel=-4.0 m/s²`、20 Hz，也只能每个周期改变目标约 `0.2 m/s`；如果反馈跟不上，实际刹车距离不保证达到理想的 `4.0 m/s²`。
- 直接继续提高 MPPI 峰值速度会让上述反向距离变长。先使规划路径和障碍图稳定，再量测实际减速度并按实测能力调整 smoother/控制器预测，才是可控的提速方式。

## 3. 为什么先折线，过冲后又能直走

### 当时的实际代价图并不允许直接穿过

对每一条已发布 global path，以最近的 global raw costmap 对“当前位置直连 Bed3”取样；该 costmap 最多约滞后 `0.5 s`，不是 planner 内部同一帧，因此结论是强证据而非绝对复现。

第3次：

| 时刻 | 位置 | 直线最高 cost | 直线硬阻塞采样格 | path/直线长度 |
|---|---|---:|---:|---:|
| 23:59:53.652 | (3.47, -0.50) | 254 | 150 | 3.483 / 2.572 m |
| 23:59:54.808 | (3.57, -1.94) | 253 | 78 | 1.913 / 1.843 m |
| 23:59:55.802 | (4.10, -2.13) | 207 | 0 | 1.426 / 1.306 m |
| 23:59:58.803 | (4.37, -2.16) | 253 | 97 | 1.144 / 1.031 m |

初始直线确实穿过 `253/254` 的禁行/内切膨胀格，不能安全地硬拉直。车因过冲到了锥桶下侧/旁侧后，起点改变，`23:59:55.802` 的直线已无硬阻塞，于是路线接近直线。之后代价图又变化，硬格重新出现，路径也会再次调整。

### 规划器与平滑器使折线更明显

- 自定义规划器以 `max(|body_x|/x_speed, |body_y|/y_speed)` 估算每段时间（`clearance_planner.cpp` 约第 879 行）。它没有计入加速度、减速度和横纵速度方向切换成本。对于现在的十字型全向底盘，折线在这个理想模型下不比直线慢很多，实车却要承担反向和横移的动态代价。
- 圆角功能已启用，不是完全没做：目标半径 `0.75 m`、最低 `0.55 m`、最短直段 `0.50 m`。但每个圆角都会进行 cost/足迹校验；无净空时会保留折角。日志中的 smooth collision rejection 表明不能仅靠“提高平滑强度”解决，强行平滑会更多回退或损失安全裕量。
- planner 把 `cost >= 253` 当不可通行，且仍有 `costmap_weight=3.0`。鬼影或膨胀格靠近通道时，自然优先选择绕行。
- 日志多次出现 retained route blocked。旧路径重用在新地图中被阻塞时也会触发换路，造成 RVIZ 路径在动态 costmap 下跳变。

## 建议的验证次序

1. **先修时间戳/TF一致性并录包复测**。验收条件：机器人运动时，静态补充圆盘不再在地图中拖尾；`held_tracks` 不应把一个固定环境碎片扩散为多处 lethal 团。
2. **再验证代价图**。先保持 `robot_radius=0.23 m` 和 `inflation_radius=0.60 m, cost_scaling_factor=8.0` 不变，比较修复前后 Bed3 直连线的 `253/254` 格数量、optimizer fail 和 Approach 次数。此时才有可信依据调整膨胀参数。
3. **最后调整控制**。测量真实线减速度和反向距离。若稳定路径上仍出现反向滞后，再调 smoother 的反馈窗口/加减速度，并优先让 planner 的时间代价包含加减速与横纵切换成本；不要首先再提高最大巡航速度。
4. **完善下一包录制**。除点云和 OPS 校准外，保留 `/trajectories`、raw/smoothed/controller path、global/local raw costmap、所有速度链路和 wheel diagnostics。这样每次即可将“感到鬼影/过冲”对应到具体时刻、具体点云和具体命令层。
