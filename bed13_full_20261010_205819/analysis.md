# 20261010_205819 四次运行与过冲分析

分析时间：2026-10-10 21:26（Asia/Shanghai）。

数据：本目录的 `timeline.jsonl`、`rosbag/rosbag_0.db3`、`journal.log`、`snapshot.txt`；对照为 `bed13_full_20261010_195852`。结合当前 STM32、NUC 源码核对。本次仅增加分析脚本、图片与报告，没有修改生产代码。

## 结论

存在明显的导航转弯偏离，但不能把它简单归因于“STM32 轮速斜坡让车减不下来”。直接证据是：MPPI 已要求换向，NUC 的 ROS `velocity_smoother` 仍在下发旧方向速度；两个典型弯点分别持续约 **0.36 s、0.58 s**，之后还有电机响应和反馈差异。

当前 STM32 导航速度斜坡主要限制加速：同方向降低速度、归零、换向时撤销旧方向目标，都没有采用对称的慢减速规则。床位 `SetMoveTgt` 位置闭环中的另一层斜坡则是对称的，必须区分。

更准确的问题是：**MPPI 要求的速度变化，与后处理链路实际允许的变化、底盘实际响应及控制器收到的速度反馈不一致。** 十字底盘可以保持车头不转而横移，但 20 kg 车体改变平移速度方向仍需要制动力和时间。取消转角限速并不消除这个约束。

## 2. 实际速度链路有多层，不能只看 STM32

```text
MPPI /cmd_vel_nav
  → ROS velocity_smoother /cmd_vel
  → 床位 / Home / 场地约束 /cmd_vel_home_limited
  → Collision Monitor /cmd_vel_safe
  → NUC bridge 加速约束及发送
  → STM32 导航加速斜坡
  → 电机轮速响应
```

当前 YAML 中 ROS 速度平滑器为：

```yaml
smoothing_frequency: 20.0
feedback: OPEN_LOOP
scale_velocities: false
max_accel: [2.5, 2.2, 1.8]
max_decel: [-2.0, -2.6, -2.0]
```

单位分别为平移 `m/s²`、旋转 `rad/s²`。`OPEN_LOOP` 使用此前平滑器输出作为基准；它不是使用当前 `/odom` 速度重新起算。

采集脚本没有保存 velocity_smoother 的运行参数 dump，所以不能直接用工作区 YAML 证明所有参数均已部署。但本包实际 Y 制动阶梯为每约 `50 ms` 改变 `0.13 m/s`，与 `2.6 m/s²` 一致。这一项由运行数据得到验证。

桥接层还有 `gate_release_wheel_accel_m_s2: 2.8`，STM32 导航层还有约 `2.786 m/s²` 的加速限制。多层约束会影响新方向速度建立，但不应把所有层都理解成对称的减速斜坡。

## 3. 典型过冲按时间戳核对

以下以首次 MPPI Y 命令变为相反方向为 `t=0`。ROS 各层采用同一个采集进程的消息接收时间；电机诊断采用 STM32 `stamp_cs` 分重启周期估计时钟偏移，只能用于近似时序比较。

| 首次发出 / 测得相反 Y 方向 | 第 3 次：护士台→床 1 | 第 4 次：床 1→床 3 |
|---|---:|---:|
| MPPI 换向时刻 | 21:00:20.501 | 21:01:30.881 |
| ROS 速度平滑器 | +0.361 s | +0.584 s |
| 床位 / Home 限制后 | +0.361 s | +0.586 s |
| Collision Monitor 后 | +0.384 s | +0.626 s |
| bridge 实际发送 | +0.385 s | +0.627 s |
| STM32 斜坡后轮速目标，估计 | +0.435 s | +0.695 s |
| 测得轮速，估计 | +0.635 s | +0.795 s |

**这个表的关键是：STM32 尚未收到相反方向指令时，上游就在持续要求旧方向运动。** 各行延迟是相对同一 MPPI 时刻的累计值，不应再次相加；首次过零也不等同于一个系统固定的纯延迟。

### 第 3 次护士台→床 1

对应录制起点后 `119.628969 s`。换向时 MPPI `vy≈−0.276 m/s`，平滑器此前仍为 `+0.938 m/s`，直到约 `0.361 s` 后才变为负方向。

### 这些偏离没有把 RViz 候选路径误当执行路径

额外解码了 `/plan`、`/plan_smoothed`、`/transformed_global_plan`。两处弯点的平滑几何确实出现在控制器发布的 `/transformed_global_plan` 中：

| 参考路径到旧方向极值的距离 / m | 第 3 次床 1 | 第 4 次床 3 |
|---|---:|---:|
| 换向前原始 `/plan` | 0.445 | 0.602 |
| 换向前 `/plan_smoothed` | 0.505 | 0.627 |
| 换向前控制器 `/transformed_global_plan` | 0.505 | 0.627 |

原始和平滑路径在 `map`，控制器路径在 `odom`；本包 `/tf_static` 确认 `map→odom` 为单位变换，因此可以直接比较坐标。后续重新规划会从已经偏离的位置生成新路径，若只比较当时的新路径，会低估此前发生的偏离，所以这里使用冻结参考。

并非“没有执行平滑路径”。这两处有圆滑路径，问题在于车辆速度变化没有跟上要求。

## 4. STM32 导航斜坡和床位位置斜坡的区别

### 导航速度模式

`Program/Core/Src/DJIMotorCtrlSTM32.cpp` 的 `slew_command()`：

1. 目标为零，直接返回零。
2. 目标与当前符号相反，先把当前命令清零，再限制新方向加速。
3. 同方向目标绝对值减小，直接返回更小目标。
4. 主要对增加速度的过程施加 `350 wheel RPM/s` 约束。

152 mm 轮径对应约 `2.786 m/s²`。因此当前导航源码没有在收到减速指令后还按对称斜坡维持较高旧目标的逻辑。**命令立即降低不意味着车体速度立即降低**，电机闭环、车体惯性、轮地接触仍会影响实际减速。

日志中，导航段的 STM32 斜坡后目标与测得轮速，时间平移拟合通常约 X `0.07–0.12 s`、Y `0.06–0.09 s`；195852 对照也相近。它们是跟随曲线的统计指标，不是串口或电机固定延迟。大速度阶跃完整爬升可能仍耗时 `0.4–0.7 s`，不能把爬升耗时全部当作执行前等待。

全包电流饱和标志只有 4 条诊断记录，且两处重点弯点所在导航段没有饱和标志。没有看到“持续电流饱和”足以解释主要偏离的证据；约 20 Hz 的诊断采样也不能排除更短的电流峰值。

### 床位 SetMoveTgt 位置闭环

`Program/Core/Src/ChassisCtrl.c` 的 `chassis_ctrl_slew()` 是普通对称斜坡，XY 为 `300 wheel RPM/s ≈ 2.388 m/s²`。减速、换向也会逐步变化，之后还经过底层速度处理。

这一层确实值得单独检查低速对准的停止与反复修正。但本报告两处大偏离都发生在导航状态 `3`、`6` 内，不能用床位位置闭环斜坡解释它们。两种模式也不宜一起删除所有斜坡。

本包没有固件校验值，源码核对不能代替确认实际烧录版本；运行诊断的目标与轮速则提供了独立的行为证据。

Approach 在两处换向前已经介入，会降低旧方向速度，同时也缩小新方向分量；它是保护层介入后的额外轨迹变化，不能简单当作一个应该删除的慢速层。

`goal_handoff_hold_s: 0.25` 作用于目标交接；这两个弯点发生时目标并未切换，所以不是这两处偏离的直接原因。减少交接等待与解决导航中制动不一致是两个问题。

## 7. 下一步提速应该如何做

### 第一优先级：让制动要求与底盘响应匹配

用直线减速和换向数据分别确定 X/Y 可重复达到的制动能力，再决定平滑器 `max_decel`。如果实际制动能力明显大于当前设置，适度提高其绝对值可以减少后处理保留旧方向的时间；若实际能力不足，单纯提高数值只会把困难转移到轮速闭环，甚至增加偏离。

例如，平滑器仍为 `1.517 m/s` 时，以 `2.6 m/s²` 减至零，需要约 `0.584 s`、`0.443 m`。把命令制动提高到 `3.6 m/s²`，理想命令过零时间约 `0.421 s`，可缩短约 `0.163 s`；这只是条件计算，不是本车已经验证的制动能力，也不是保证节省的全程时间。

当前两个包控制器参数一致，主要问题也不是 `PathFollowCritic` 没有生效。实际权重为普通行驶 `16`、床 1→床 3 `14`、护士台 `10`。继续提高跟随权重，不会让仍在输出旧方向的平滑器或底盘瞬间改变方向。

### 第二优先级：提前塑造弯点速度，而不是等到弯点再反向拉回

十字底盘可以取消依赖车头转向能力的限制，但路径曲率仍对应平移加速度：

```text
曲线路径：a_normal = v² × curvature
直线制动：distance_stop ≈ v² / (2 × a_brake)
```

即使车头保持不变，从沿 Y 运动改为沿 X 运动，原有 Y 速度仍要减小，X 速度仍要建立。以 `2.2 m/s` 和 `2.6 m/s²` 为例，单轴理想制动距离约 `0.93 m`；这不是日志该弯点的精确距离，而是说明高速改变速度方向需要提前量。

应保留现有有净空的圆滑路径，并根据实测制动能力在弯前开始调节速度。适合十字底盘的约束应围绕平移速度向量变化及轮速能力，不能直接把旧 X-drive 的转角限速数值原样搬回，也不能认为全向底盘所有弯点都可以满速通过。

Humble MPPI 的本次运行快照没有 ax/ay 加速度限制参数。不要只向 YAML 添加其他版本的参数就认定预测模型已受到同样约束；需要核对安装版本，或者在实际有效的速度与轨迹处理层实现一致的限制。

### 第三优先级：改善反馈，并用相同路线做对照

先补录 `/medical_nav/ops_raw_pose`、`/medical_nav/ops_calibration` 与当前已有的各级 cmd、轮速诊断、`/odom`、执行路径，核对原始位置、融合速度与实际制动。

评估融合速度的动态响应，尤其是 Y 轴制动期间对旧速度的保持。当前不能直接建议把平滑器切为 `CLOSED_LOOP`：它会使用 `/odom`，而本包已经显示该反馈存在动态滞后。

随后每次只改变一个因素，用同一正式路线至少连续三次，比较全程均值、最慢一次、弯点最大路径偏离、MPPI 失败、Stop / Approach 以及实测速度。优先降低失败和回拉，不把巡航峰值当作唯一目标。
